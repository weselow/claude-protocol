# 2026-09-17 — проверка отчёта о завершении, которая действительно останавливает

Хук `validate-completion.cjs` (событие SubagentStop) должен был возвращать к
работе субагента, который отчитался о завершении, не доделав. Замер по журналам
всех проектов на машине разработчика: около 790 срабатываний, 266 раз хук
«хотел остановить» — и ни одного раза не остановил. Две причины:

- `block()` в режиме `bypassPermissions` печатала предупреждение и выходила с
  кодом 0. У SubagentStop такой вывод до модели не доходит: он ложится в журнал
  субагента уже после его завершения. Ведущий не упомянул его ни разу.
- 165 из 266 тревог были ложными: путь к рабочей копии строился из
  идентификатора задачи, а в проектах с префиксом задача `bd_1c-oko-219` живёт в
  `.worktrees/bd-219`.

Остальное тоже было мёртвым: определение типа субагента искало в журнале поле
`parentToolUseID`, которого там нет, и инструмент `Task`, который теперь
называется `Agent`; ветки «supervisor/worker» остались от второй версии.

## Что сделано

Хук переписан маленьким. Отчёт берётся из поля `last_assistant_message`,
которое Claude Code передаёт в SubagentStop (проверено замером), — журнал
больше не разбирается. Отчётом считается сообщение, в котором строка
начинается с `BEAD <id> COMPLETE` (знак заголовка или жирный шрифт перед ней
допустимы); разбирается только текст от этой строки. Всё остальное
пропускается. Проверки по порядку, каждая останавливает с причиной, в которой
сказано, что сделать:

1. Раздел `Checklist:` есть, в нём есть пункты, и все отмечены. Пунктом
   считается строка с `-`, `*`, `+` или номером и квадратными скобками.
   Раздел кончается на первой строке, которая не пункт и не сдвинута глубже
   метки, — открытый пункт под «Found along the way:» в счёт не идёт.
2. Строка `Worktree:` есть (метка может быть жирной целиком или до
   двоеточия), путь — из кавычек, если они есть, иначе первое похожее на путь
   слово; пояснение и точка после пути отбрасываются, путь на следующей
   строке тоже принимается. На Windows `/c/…` из Git Bash превращается в
   `C:/…`. Относительный путь считается от корня проекта. Каталог должен
   существовать и быть рабочей копией git; причина называет путь.
3. `git -C <рабочая копия> status --porcelain` пуст; в причине — сам вывод.
4. Если у рабочей копии есть origin: полное имя ветки из
   `git symbolic-ref -q HEAD` (неудача — HEAD отсоединён, останавливаем) есть
   в `ls-remote --heads origin` и указывает на тот же коммит, что HEAD.
   Если `ls-remote` сам упал (`execCommand` вернул `null`: нет сети, неверный
   адрес) — не останавливаем. Пустой ответ (`''`) — ветки нет, останавливаем.
   Подсказка — `git push -u origin HEAD`: её не сбивает метка git (tag) с тем же именем.

`stop_hook_active: true` — пропускаем: субагента уже возвращали, спорить по
кругу незачем. Ранний выход по `hasBeads()` остался.

`block()` в `hook-utils.cjs` теперь останавливает в любом режиме. Её вызывает
только этот хук. `deny()` и `ask()` для PreToolUse не тронуты — там
предупреждение до модели доходит.

Тесты: `tests/hooks/validate-completion.test.js` — настоящие временные
репозитории, голый репозиторий в роли origin, git без глобальных настроек
машины (`GIT_CONFIG_GLOBAL` на пустой файл), чтобы подпись коммитов или чужие
перехватчики не влияли на результат. Тесты, которые ничего не меняют, делят
один проект: создание репозиториев занимает большую часть времени.

## Что проверять первым, если сломается

- **Хук снова никого не останавливает.** Приходит ли `last_assistant_message`:
  временно записать stdin хука в файл и запустить субагента. Если Claude Code
  переименует поле — хук молча пропускает всё.
- **Хук останавливает зря.** Причина называет путь или ветку — сверить с тем,
  что субагент написал в `Worktree:`. Разбор отчёта — `findLabel`,
  `checklistMarks`, `pathIn` в `templates/hooks/validate-completion.cjs`; новую
  форму записи сначала добавить в `it.each` тестов.
- **Хук висит.** `ls-remote` ограничен 10 секундами (`execCommand`), запрос
  пароля в терминале выключен `GIT_TERMINAL_PROMPT=0`. Окно диспетчера учётных
  данных Windows эта переменная не отключает.
- **Субагент застрял в цикле.** Проверить, что `stop_hook_active` приходит как
  логическое `true`, а не строкой.

## Что осознанно не тронуто

- Подключение хука в Codex — отдельная задача.
- Маркеры отчёта `BEAD {BEAD_ID} COMPLETE`, `Worktree:` и `Checklist:` — их
  закрепляет `tests/test_bootstrap.py`; `Worktree:` добавлен туда при проверке.
- `bash-guard.cjs`, `session-start.cjs`.
- `approve()` по-прежнему печатает `{"decision":"approve"}`; работает, менять
  не просили.
- Отсоединённый HEAD останавливается отдельной причиной; других особых случаев
  для ветки нет.
- Каталог внутри проекта, который сам не рабочая копия (`.worktrees/лишний`),
  проходит как рабочая копия главного каталога: git находит её выше. Сверять
  верхний каталог git с путём не стали — на Windows короткие имена и регистр
  букв дали бы ложные остановки, ради которых всё и переписано.
- Путь с пробелами без кавычек не разбирается; в кавычках — разбирается.

## Раунд проверки

Независимая проверка коммита `4acd4b6` нашла ложные остановки и воспроизвела
каждую на настоящих репозиториях:

- маркер отчёта находился в любом месте — цитата «BEAD … COMPLETE» в сводке
  проверяющего вызывала остановку;
- значением `Worktree:` была вся строка — ломалось на «(branch x)», «— pushed»,
  точке в конце, ссылке, метке `**Worktree**:`, пути на следующей строке и
  пути Git Bash;
- пункты `* [ ]` и `2. [ ]` проходили, `- [ ]` вне чеклиста останавливал с
  неверной причиной, пустой чеклист проходил;
- метка с тем же именем, что ветка, превращала `rev-parse --abbrev-ref HEAD`
  в `heads/x` и давала ложное «ветки нет на origin»;
- путь на каталог, который не рабочая копия git, проходил;
- `REPORT_MARKERS` не закреплял `Worktree:`, тест «HEAD впереди origin»
  проверял только текст, общий с другой причиной.

Всё исправлено с тестами, написанными до кода (15 новых проверок падали на
прежнем хуке). Ещё до этой проверки хук остановил отчёт о собственной
переделке: пункт чеклиста упоминал маркер пустого пункта посреди текста.
