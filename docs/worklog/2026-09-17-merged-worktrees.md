# 2026-09-17 — слитые рабочие копии снова видны

Проверка при старте сессии должна напоминать о рабочих копиях (git worktree)
в `.worktrees/bd-*`, чья ветка уже слита. Она не сработала ни разу, и ничто об
этом не говорило. В другом проекте за это время накопилось два десятка
брошенных каталогов и семь десятков веток на сервере. Причин оказалось три, и
любой хватало, чтобы проверка молчала:

- git спрашивали о ветке, буквально названной `main`. В репозитории с `master`
  git отвечал ошибкой, `execCommand` возвращал `null`, список слитых был пуст;
- запрос на слияние (PR), слитый со сжатием в один коммит (squash), git
  слитым не считает: вершина ветки не становится предком основной;
- обычный вывод `git branch` ставит `+ ` перед веткой, занятой рабочей копией,
  а код срезал только `* `. Ветка из `.worktrees/bd-*` занята всегда, так что
  имена не совпадали даже на `main`.

## Что сделано

В `collectMergedWorktrees` (`templates/hooks/session-start.cjs`):

- основная ветка берётся из `git symbolic-ref refs/remotes/origin/HEAD`, без
  него — `main`, затем `master`;
- слитые ветки берутся из двух источников: `gh pr list --state merged` и
  `git branch --format=%(refname:short) --merged <основная>`. Спрашивают их,
  только если есть хоть одна рабочая копия `bd-*`;
- не ответил ни один источник — в выводе предупреждение, а не тишина;
- номер задачи и «ещё открыта» печатаются, только если `bd show` вернул ровно
  этот номер. `bd show` находит задачу и по части номера, так что совпадение
  по части не считается. Иначе названа ветка, и задачу агент ищет сам;
- для уборки предлагаются `git worktree remove --force` и `git worktree prune`:
  `bd worktree remove` на Windows сломан (u51).

Нашлось по ходу, при проверке на живом репозитории: `git branch --merged`
считает слитой и ветку, в которой ещё не было ни одного коммита, ведь её
вершина тоже лежит в истории основной ветки. Это любая только что созданная
рабочая копия, и совет был бы удалить её с `--force`, пока в ней работают.
Поэтому git-источник засчитывает ветку, только если в её журнале ссылок
(reflog) есть запись о коммите. Из трёх способов выбран этот: поиск вершины
среди вторых родителей слияний пропускает слияние перемоткой (fast-forward), а
отсев веток на вершине `main` не спасает, когда `main` уже ушёл вперёд.

## Что проверять первым, если сломается

- **Проверка снова молчит.** Запустить руками то же, что она:
  `git worktree list --porcelain`, `git symbolic-ref refs/remotes/origin/HEAD`,
  `git branch --format=%(refname:short) --merged <ветка>`,
  `gh pr list --state merged --json headRefName`. Если ветка есть в выводе
  git, но не сообщается, смотреть `git reflog show refs/heads/<ветка>`: без
  записи `commit` ветка не засчитывается.
- **Слитой назвали рабочую копию, в которой идёт работа.** Первым делом
  `hasOwnCommits`: ветка без своих коммитов, но с записью `commit` в журнале,
  например после `git reset` на основную ветку.
- **Номер задачи не выводится, хотя задача есть.** Имя ветки не совпадает с
  `bd-<номер задачи>` в точности — так и задумано.
- **Тесты с подменными `gh` и `bd` падают только на Windows.** В
  `tests/hooks/session-start.test.js` подмена — это `.cmd`, а Node ищет
  `gh.exe` раньше, поэтому каталоги с настоящими `gh` и `bd` из PATH убраны.
  `%~dp0` в такой обёртке не работает: `.cmd`, найденный через PATH и
  вызванный по имени в кавычках, получает из него не тот каталог.
