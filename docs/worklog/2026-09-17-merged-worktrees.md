# 2026-09-17 — слитые рабочие копии снова видны

Проверка при старте сессии должна напоминать о рабочих копиях (git worktree)
в `.worktrees/bd-*`, чья ветка уже слита. Она не сработала ни разу, и ничто об
этом не говорило. В другом проекте за это время накопилось два десятка
брошенных каталогов и семь десятков веток на сервере. Причин оказалось три, и
любой хватало, чтобы проверка молчала:

- git спрашивали о ветке, буквально названной `main`. В репозитории с `master`
  git отвечал ошибкой, `execCommand` возвращал `null`, список слитых был пуст;
- запрос на слияние (PR), слитый со сжатием в один коммит (squash), git
  слитым не считает: вершина ветки не становится предком основной;
- обычный вывод `git branch` ставит `+ ` перед веткой, занятой рабочей копией,
  а код срезал только `* `. Ветка из `.worktrees/bd-*` занята всегда, так что
  имена не совпадали даже на `main`.

## Что сделано

В `collectMergedWorktrees` (`templates/hooks/session-start.cjs`):

- основная ветка — имя из `git symbolic-ref refs/remotes/origin/HEAD`, без него
  `main`, затем `master`. Сравнение идёт с `refs/remotes/origin/<имя>`, если
  такая ссылка есть: местный `main`, который давно не обновляли, не знает о
  свежих слияниях;
- источников два, и спрашивают их, только если есть хоть одна рабочая копия
  `bd-*`:
  - GitHub: `gh pr list --repo <владелец/имя из origin> --state merged`. Без
    `--repo` `gh`, у которого не выбран репозиторий по умолчанию, отвечал про
    исходный репозиторий форка — пустым списком и без ошибки. Если origin не на
    GitHub, этот источник считается не ответившим. При пяти рабочих копиях и
    меньше каждая ветка спрашивается по имени (`--head`), так находится и давнее
    слияние; при большем числе — один список из 200 последних;
  - git: `git branch --format=%(refname:short) --merged <основная>`;
- ни одному ответу не верим на слово:
  - git перечисляет любую ветку, чья вершина лежит в истории основной: и
    свежую, и ту, где коммит отменили через `git reset`. Поэтому ветка
    засчитывается, только если её текущая вершина записана в журнале ссылок
    ветки (reflog) как коммит;
  - GitHub знает только имена веток, а короткие имена повторяются. Поэтому
    PR засчитывается, только если его слитая вершина (`headRefOid`) совпадает
    с вершиной рабочей копии или идёт после неё, и только для ветки, в которой
    кто-то делал коммиты;
  - журнала у ветки нет (git стирает его через 90 дней, а при
    `core.logAllRefUpdates=false` не пишет вовсе) — выводится «похоже, слита,
    проверьте вручную» без команды удаления;
- не ответил ни один источник — в выводе предупреждение, а не тишина;
- команда уборки `git worktree remove --force` и `git worktree prune`
  (`bd worktree remove` на Windows сломан, u51) выводится только для чистой и
  не запертой рабочей копии. Если в копии есть несохранённые изменения или её
  состояние не читается, выводится просьба посмотреть вручную. Запертая копия
  так и называется: одного `--force` ей мало, а `&&` пропустил бы `prune`;
- номер задачи и её состояние печатаются, только если `bd show` вернул ровно
  этот номер. `bd show` находит задачу и по части номера, так что совпадение
  по части не считается. Иначе названа только ветка, задачу агент ищет сам.

## Круг ревью

Первый вариант (коммит `cba0d19`) независимое ревью вернуло с находками, и
все они воспроизводились. Главная: признаком «в ветке были коммиты» служила
любая запись `commit` в журнале ветки. После `commit` и `git reset HEAD~1`
ветка снова лежала в истории основной и считалась слитой, выводилась команда
`remove --force`, и её выполнение удаляло несохранённый файл. Исправлено
проверкой текущей вершины, а сверх того добавлена страховка: команда с
`--force` никогда не выводится для копии с несохранёнными изменениями,
что бы ни решила проверка слияния. Остальное из того же круга: сверка PR по
вершине, а не по имени; `--repo` из origin; сравнение с копией основной ветки
с сервера; явное сообщение для ветки без журнала; запертые копии. В первом
отчёте было написано «16 новых тестов», на деле их было 13; сейчас новых 25,
всего в файле 28.

## Что проверять первым, если сломается

- **Проверка снова молчит.** Запустить руками то же, что она:
  `git worktree list --porcelain`, `git symbolic-ref refs/remotes/origin/HEAD`,
  `git branch --format=%(refname:short) --merged <ссылка>`,
  `gh pr list --repo <владелец/имя> --state merged --head <ветка> --json headRefName,headRefOid`.
  Если ветка есть в выводе git, но не сообщается, смотреть
  `git reflog show --format="%H %gs" refs/heads/<ветка>`: вершина должна
  стоять на записи `commit`. Если ветка есть у GitHub — сравнить `headRefOid`
  с `HEAD` рабочей копии.
- **Слитой назвали рабочую копию, в которой идёт работа.** Команда удаления
  при этом всё равно не выводится, если в копии есть несохранённые изменения.
  Причину искать в `mergeVerdict` и `branchHistory`.
- **Предупреждение «could not tell» там, где GitHub есть.** `githubRepo`
  не разобрал адрес origin: поддерживаются `https://github.com/…`,
  `git@github.com:…` и `ssh://git@github.com/…`. GitHub Enterprise не
  поддерживается сознательно.
- **Номер задачи не выводится, хотя задача есть.** Имя ветки не совпадает с
  `bd-<номер задачи>` в точности — так и задумано.
- **Тесты с подменными `gh` и `bd` падают только на Windows.** В
  `tests/hooks/session-start.test.js` подмена — это `.cmd`, а Node ищет
  `gh.exe` раньше, поэтому каталоги с настоящими `gh` и `bd` из PATH убраны;
  если git лежит там же, тест сразу говорит об этом. `%~dp0` в такой обёртке
  не работает: `.cmd`, найденный через PATH и вызванный по имени в кавычках,
  получает из него не тот каталог.

  задача.

  `--repo` и в форке может отвечать про чужой репозиторий.
- Ветка, которую перебазировали перед слиянием в проекте без GitHub: её
  вершину создал `rebase`, а не `commit`, так что git-источник её не
  засчитает. Проверка здесь промолчит — это безопаснее, чем посоветовать
  удалить лишнее.
- Каталоги, у которых регистрацию в git сняли, а файлы остались: `git worktree
  list` их не показывает, и эта проверка их не видит.
