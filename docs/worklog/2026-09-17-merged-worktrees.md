# 2026-09-17 — слитые рабочие копии снова видны

Проверка при старте сессии должна напоминать о рабочих копиях (git worktree)
в `.worktrees/bd-*`, чья ветка уже слита. Она не сработала ни разу, и ничто об
этом не говорило. В другом проекте за это время накопилось два десятка
брошенных каталогов и семь десятков веток на сервере. Причин оказалось три, и
любой хватало, чтобы проверка молчала:

- git спрашивали о ветке, буквально названной `main`. В репозитории с `master`
  git отвечал ошибкой, `execCommand` возвращал `null`, список слитых был пуст;
- запрос на слияние (PR), слитый со сжатием в один коммит (squash), git
  слитым не считает: вершина ветки не становится предком основной;
- обычный вывод `git branch` ставит `+ ` перед веткой, занятой рабочей копией,
  а код срезал только `* `. Ветка из `.worktrees/bd-*` занята всегда, так что
  имена не совпадали даже на `main`.

## Что сделано

Всё в `collectMergedWorktrees` и функциях под ней
(`templates/hooks/session-start.cjs`). Источники спрашивают, только если есть
хоть одна рабочая копия `bd-*`.

**Основная ветка** (`resolveMainBranch`) — имя из
`git symbolic-ref refs/remotes/origin/HEAD`, без него `main`, затем `master`.
Сравнение идёт с `refs/remotes/origin/<имя>`, если такая ссылка есть: местный
`main`, который давно не обновляли, не знает о свежих слияниях. Нет основной
ветки — не спрашивается ни один источник.

**Источники слияний:**

- git: `git branch --format=%(refname:short) --merged <ссылка>`. Ответ
  засчитывается, только если текущая вершина ветки записана в её журнале ссылок
  (reflog) как коммит (`branchHistory`). Иначе git назвал бы слитой и свежую
  ветку, и ветку, где коммит отменили через `git reset`;
- GitHub (`mergedPullRequests`): один запрос
  `gh pr list --repo <владелец/имя из origin> --state merged --limit 200 --json headRefName,headRefOid,baseRefName`.
  PR засчитывается, если он влит в основную ветку (`baseRefName`), его вершина
  (`headRefOid`) совпадает с вершиной рабочей копии или идёт после неё, и в
  ветке кто-то делал коммиты. Адрес origin разбирает `githubRepo`: https, ssh,
  вид `git@github.com:…`, порт, `ssh.github.com`, псевдоним хоста
  `github.com-<имя>`, любой регистр букв. origin не на GitHub — источник
  считается не ответившим;
- у ветки нет журнала ссылок — выводится «похоже, слита, проверьте вручную»
  без команды удаления;
- не ответил ни один источник — в выводе предупреждение, а не тишина.

**Уборка** (`cleanupLines`). Что бы ни решила проверка слияния, команда
`git worktree remove "<путь>" && git worktree prune` выводится только для не
запертой копии, которую `worktreeIsClean` прочитала как чистую:

- `isLinkedWorktreeRoot`: `git -C` ответил из корня именно этой рабочей копии
  (пустой префикс, каталог git отличается от общего). Копия без файла `.git`
  иначе читалась бы как основной каталог;
- `git status --porcelain --untracked-files=all --ignore-submodules=none` пуст;
- в `git ls-files -v` у всех файлов пометка `H`: пометка `S` (skip-worktree)
  и строчные буквы (assume-unchanged) значат изменения, которых `status` не
  показывает.

Команда без `--force`: собственная проверка git остаётся вторым рубежом.
Подсказка говорит, что игнорируемые файлы вроде `.env` удаляются вместе с
каталогом. Если копия не чистая или не читается, выводится «посмотрите
вручную»; запертая так и называется. `bd worktree remove` на Windows сломан
(u51), правила разрешают команды git.

**Номер задачи** печатается, только если `bd show` вернул ровно этот номер.
`bd show` находит задачу и по части номера, так что совпадение по части не
считается. Иначе названа только ветка, задачу агент ищет сам.

## Первый круг ревью (на `cba0d19`)

Все находки воспроизводились. Главная: признаком «в ветке были коммиты»
служила любая запись `commit` в журнале ветки. После `commit` и
`git reset HEAD~1` ветка снова лежала в истории основной, считалась слитой,
выводилась команда `remove --force`, и её выполнение удаляло несохранённый
файл. Исправлено проверкой текущей вершины; добавлена страховка — проверка
чистоты копии перед подсказкой. Остальное: сверка PR по вершине, а не по
имени; `--repo` из origin (без него `gh` отвечал про исходный репозиторий
форка пустым списком); сравнение с копией основной ветки с сервера; явное
сообщение для ветки без журнала; запертые копии. В первом отчёте было
написано «16 новых тестов», на деле их было 13.

## Второй круг ревью (на `bca086b`)

Страховка оказалась дырявой, и два случая ревьюер довёл до удаления данных:

- `git status --porcelain` подчиняется `status.showUntrackedFiles=no` —
  неотслеживаемый файл не виден, подсказка выводилась. Простой
  `git worktree remove` при этой настройке тоже удаляет такой файл, так что
  наша проверка здесь единственная защита;
- изменения в файлах с пометкой skip-worktree или assume-unchanged и в
  подмодуле с `ignore = all` в `status` не видны;
- копия без файла `.git` читалась как основной каталог.

Исправлено тремя проверками в `worktreeIsClean` (см. выше). Кроме того:
подсказка теперь без `--force`; вместо запроса по каждой ветке (4–6,5 с
здесь, до 50 с при зависшей сети) — один запрос к GitHub; проверяется ветка,
в которую влит PR; разбор адреса origin принимает псевдонимы хоста, порт и
любой регистр; `mergeVerdict` разделена ради сложности меньше 10; тесты
убирают за собой временные каталоги (их накопилось больше тысячи, старые
удалены). Сейчас в `tests/hooks/session-start.test.js` 37 тестов, из них
34 новых.

## Что проверять первым, если сломается

- **Проверка снова молчит.** Запустить руками то же, что она:
  `git worktree list --porcelain`, `git symbolic-ref refs/remotes/origin/HEAD`,
  `git branch --format=%(refname:short) --merged <ссылка>`,
  `gh pr list --repo <владелец/имя> --state merged --limit 200 --json headRefName,headRefOid,baseRefName`.
  Если ветка есть в выводе git, но не сообщается, смотреть
  `git reflog show --format="%H %gs" refs/heads/<ветка>`: вершина должна
  стоять на записи `commit`. Если ветка есть у GitHub — сравнить `headRefOid`
  с `HEAD` рабочей копии и `baseRefName` с основной веткой.
- **Команда удаления выведена для копии с работой.** Первым делом
  `worktreeIsClean` и `isLinkedWorktreeRoot`: какой из трёх вызовов git
  ответил «чисто», хотя это не так.
- **Про слитую чистую копию говорят «посмотрите вручную».** Смотреть
  `git -C <копия> ls-files -v | grep -v "^H "` — частичная выгрузка
  (sparse checkout) помечает файлы `S`, и такая копия чистой не считается.
- **Предупреждение «could not tell» там, где GitHub есть.** Не найдена
  основная ветка или `githubRepo` не разобрал адрес origin.
- **Номер задачи не выводится, хотя задача есть.** Имя ветки не совпадает с
  `bd-<номер задачи>` в точности — так и задумано.
- **Тесты с подменными `gh` и `bd` падают только на Windows.** В
  `tests/hooks/session-start.test.js` подмена — это `.cmd`, а Node ищет
  `gh.exe` раньше, поэтому каталоги с настоящими `gh` и `bd` из PATH убраны;
  если git лежит там же, тест сразу говорит об этом. `%~dp0` в такой обёртке
  не работает: `.cmd`, найденный через PATH и вызванный по имени в кавычках,
  получает из него не тот каталог.

## Известные ограничения

- GitHub видит только последние 200 слитых PR: более давнее слияние со
  сжатием не будет замечено.
- GitHub Enterprise и псевдонимы хоста ssh, не начинающиеся с `github.com`,
  не распознаются — источник GitHub тогда молчит, а если молчит и git,
  выводится предупреждение.
- Нет основной ветки (ни `origin/HEAD`, ни `main`, ни `master`) — не
  спрашивается и GitHub: сверить `baseRefName` не с чем.
- Ветка, которую перебазировали перед слиянием в проекте без GitHub: её
  вершину создал `rebase`, а не `commit`, так что git-источник её не
  засчитает. Проверка промолчит — это безопаснее, чем посоветовать удалить
  лишнее.
- Копия с частичной выгрузкой (sparse checkout) или с подмодулями не получает
  команды удаления: первую мы не считаем чистой, вторую git без `--force` не
  удалит.
- Проверка открытых PR (`collectOpenPrs`) по-прежнему вызывает `gh` без
  `--repo` и в форке может отвечать про чужой репозиторий.
- Каталоги, у которых регистрацию в git сняли, а файлы остались: `git worktree
  list` их не показывает, и эта проверка их не видит.
