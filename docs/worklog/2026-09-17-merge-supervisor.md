# 2026-09-17 — агент merge-supervisor под нынешние модели

`templates/agents/merge-supervisor.md` был написан для прежних моделей:
закреплён за Opus, требования заглавными буквами («NEVER», «ALWAYS», «FULL»),
мелкие обязательные шаги вроде «прочитай 20+ строк выше и ниже». Нынешние
модели такие подчёркнутые правила выполняют с перебором, а шаги делают и без
подсказки. При этом в нём не было того, что действительно нужно в этом
процессе: связи с задачами beads, конфликтов при перебазировании и переносе
коммита, окончаний строк, файлов, которые создаются инструментами, и остановки
при неясном замысле.

## Что сделано

Агент переписан заново (задача os1):

- Поле `model` убрано — агент работает на модели сессии. `tools` записан
  строкой через запятую, как в документации Claude Code; список YAML тоже
  принимался, но описан не он.
- Спокойные формулировки с объяснением «зачем». Жёсткие границы собраны в
  раздел Limits. Всегда: не отправлять (push), не обходить перехватчики
  коммита, не переписывать историю main, не делать коммит при открытом
  вопросе. Только по прямой просьбе в задаче: менять main (здесь ведущий по
  слову пользователя сам сливает ветки задач в main локально, и довести такое
  слияние — обычная работа агента) и всё, что выбрасывает сделанное.
- Таблица трёх операций — merge, rebase, cherry-pick: как у git узнать, что
  операция идёт, что такое «ours»/«theirs» в каждой и чем продолжить.
  Главная ловушка — при rebase «ours» означает базу, а не свою ветку.
- Замысел сторон берётся из задач beads (`bd show`/`bd comments` по номеру из
  имени ветки `bd-<ID>` и из сообщений слияний), `git log --merge` и трёх
  стадий файла `:1:`/`:2:`/`:3:`.
- Отдельно: файл блокировки версий не удаляется — сначала разрешается
  описание зависимостей (`package.json`), затем менеджер пакетов запускается
  прямо по файлу с маркерами (`npm install --package-lock-only`), и разница
  против каждой стороны должна показать только её зависимости; выгрузка beads
  создаётся заново; разделы истории изменений сохраняют записи обеих сторон;
  окончания строк и кодировка остаются как были.
- Неясный замысел — остановка: уверенные файлы проиндексированы, неясные
  оставлены неслитыми, операция не завершена и не отменена, в отчёте вопросы с
  рекомендацией.
- Проверка: `git diff --check`, `git diff --cached --check`, поиск маркеров
  через `git grep`, тесты проекта вместе с новыми тестами обеих сторон.

Все команды из текста проверены на пробном репозитории с рабочей копией git
(worktree): `git diff --check` находит оставленные маркеры и до, и после
`git add`; `git diff --ours --stat` при смене LF на CRLF считает изменёнными
все строки, а с `--ignore-cr-at-eol` — только настоящие; `npm install
--package-lock-only` по `package-lock.json` с маркерами пишет файл с
зависимостями обеих веток, и `git diff --ours --stat` показывает только пакет
другой стороны; опустевший cherry-pick не проходит `--continue` («now empty»)
и снимается `--skip`, а rebase такой коммит выбрасывает сам; при add/add
стадии 1 нет.

Независимая проверка (после первого коммита) нашла два существенных
недочёта: про файлы блокировки не было сказано, с чего начать, — модель,
скорее всего, удалила бы файл и поставила всё заново, втащив в коммит слияния
непроверенные обновления; и текст утверждал, что main меняется только через
PR, хотя здесь ведущий по просьбе пользователя сливает ветки в main локально,
— агент отказался бы от самой частой своей работы. Оба исправлены.

## Что проверять первым, если сломается

- **Отчёт агента остановлен проверкой завершения (SubagentStop).** Первым
  делом — нет ли в отчёте строки с `BEAD` и `COMPLETE`: такую строку хук
  принимает за отчёт исполнителя задачи. В версии хука на main до задачи fyq
  совпадение ищется в любом месте строки, в новой — только в начале строки.
  Второе: старый хук считает «супервизорами» всех подрядчиков, в чьём типе
  есть слово `supervisor`, и требует от них отчёт по задаче — имя
  `merge-supervisor` под это подпадает. Сейчас это не срабатывает, потому что
  тип подрядчика хук определить не может (инструмент называется Agent, а не
  Task), и fyq эту ветку убирает. Если определение типа когда-нибудь оживёт,
  виновато будет имя.
- **Агент работает не на той модели.** Без `model` порядок такой: модель,
  переданная при вызове, затем переменная `CLAUDE_CODE_SUBAGENT_MODEL`, затем
  модель сессии.
- **Агент перевернул окончания строк.** Проверка `git diff --ours --stat`
  работает только до `git add` — после индексации стадий 2 и 3 уже нет. И
  `git diff --check` в CRLF-файле показывает каждую изменённую строку как
  лишний пробел в конце (это CR) — в тексте сказано, что его не трогать.
- **Агент завис на коммите или слияние получило сообщение «Merge branch …».**
  Это редактор: голый `git commit` и оба `--continue` его открывают.
  Переменная `GIT_EDITOR` важнее, чем `core.editor`, поэтому в тексте
  `GIT_EDITOR=true`, а сообщение коммита слияния передаётся через `-m`/`-F`.
- **Агент выбросил изменения другой стороны целиком.** Искать `-s ours` или
  `-X ours`/`-X theirs` в его командах: они решают до чтения, а при rebase
  `-X` меняет смысл так же, как стадии. Текст их запрещает.
- **Агент взял не ту сторону при rebase.** Смотреть строку rebase в таблице:
  при перебазировании своя работа ветки — это «theirs».
- **Агент считает, что идёт перебазировка, хотя её нет.** `REBASE_HEAD`
  остаётся после завершённой перебазировки (проверено на git 2.55), поэтому
  признак в тексте — каталог `rebase-merge`/`rebase-apply` через
  `git rev-parse --git-path`. `MERGE_HEAD` и `CHERRY_PICK_HEAD` по завершении
  исчезают. Первая версия текста эту ошибку содержала — нашлась на пробном
  репозитории после замечаний проверяющего.
- **`git log --merge` падает с «--merge without MERGE_HEAD?».** При rebase и
  cherry-pick он работает только с git 2.45; в тексте указан запасной путь.
- **В коммит слияния попали обновления зависимостей, которых не было ни на
  одной стороне.** Смотреть, как агент разбирал файл блокировки: удалил и
  поставил заново или запустил команду обновления вместо установки. В тексте
  сказано сверить `git diff --ours` / `--theirs` по этому файлу до `git add`.
- **Агент отказался доводить слияние ветки в main.** В задаче должно быть
  прямо сказано, что слияние в main просили; без этого агент main не трогает
  намеренно.
- **Выгрузка beads конфликтует в корне рабочей копии** (`/issues.jsonl`, а не
  `.beads/issues.jsonl`) — это не вопрос агента, а настройка bd:
  `bd memories issues.jsonl`.

## Что осознанно не тронуто

- `templates/CLAUDE.md`, `templates/CLAUDE-ru.md` и
  `templates/agents/code-reviewer.md` — их меняет задача pw6. Строка агента в
  CLAUDE.md («conflict resolution») осталась верной; в CLAUDE-ru.md
  («разрешение конфликтов слияния») она теперь уже, чем агент, — он разбирает
  и rebase, и cherry-pick, — но не ошибочна.
- Версия агента для Codex (TOML) — позже, отдельной задачей. Текст написан без
  имён инструментов Claude Code, чтобы его можно было перенести.
- Конфликты при `git revert` отдельно не описаны: `git status` называет и эту
  операцию, а устроена она как cherry-pick.
- Тестов на текст агента нет: это инструкция, а не код. Проверяют его слабо.
  `claude plugin validate --strict` (Claude Code 2.1.274) смотрит только поля
  заголовка, который сумел разобрать: заголовок без `description` он
  отклоняет, а файл без заголовка, пустой файл и файл с битым YAML
  пропускает. Поэтому заголовок дополнительно разобран настоящим разборщиком
  YAML (`yaml.safe_load`: три поля, все строки). `tests/test_bootstrap.py`
  только сверяет список агентов с манифестом плагина.
