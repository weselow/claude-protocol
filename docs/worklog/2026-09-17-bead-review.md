# 2026-09-17 — навык проверки задач bead-review

Задача pw6. Агент `code-reviewer` нёс собственный порядок проверки, написанный
для старых моделей: требовал блоки DEMO, которых ни одно правило не просит
исполнителя писать, сравнивал всегда `main...bd-<id>` и был закреплён за
`haiku`. Теперь порядок проверки живёт в одном месте — навыке
`templates/skills/bead-review/`, а агент стал тонкой обёрткой над ним.

## Что сделано

- `templates/skills/bead-review/SKILL.md` — весь порядок: границы полномочий,
  входные данные, первичная проверка (правила проекта → задача и комментарии →
  фиксация base/head → чтение изменений и кода вокруг → проверка по списку →
  запуск того, от чего зависит вывод), виды замечаний (дефект P1/P2/P3,
  вопрос, предложение), итог, форма отчёта, повторная проверка со сквозными
  номерами
  R1, R2…, доставка отчёта. Текст не привязан к Claude Code, кроме последнего
  короткого раздела. В заголовке только `name` и `description` — оба поля
  понимает и Claude Code, и формат Agent Skills, который читает Codex.
- `templates/skills/bead-review/handoff.md` — форма запроса на проверку и
  примеры запросов.
- `templates/agents/code-reviewer.md` — имя, описание, список инструментов
  только для чтения плюс Bash, `skills: [bead-review]`; `model:` убран, блоки
  DEMO убраны; в теле — роль и границы.
- Строки об агентах в `templates/CLAUDE.md` и `templates/CLAUDE-ru.md`
  (заодно строка merge-supervisor — по просьбе ведущего, файл самого агента не
  тронут, его переписывает os1). В `templates/rules*/implementation-standard.md`
  самопроверка теперь отсылает к `code-reviewer` и навыку; список пунктов
  остался — это требования проекта, навык сам велит их читать.
- Единственное число «skill» → «skills» в `commands/init.md`,
  `.claude-plugin/marketplace.json`, README (раздел про плагин); в README и
  README-ru — раздел о проверке задачи с примерами запросов и запись в
  «Unreleased» / «Не выпущено».
- Тесты в `tests/test_bootstrap.py`: каждый навык из `skills:` агентов есть в
  `templates/skills` и назван без префикса плагина; имя навыка совпадает с
  каталогом; у `code-reviewer` навык `bead-review`, нет инструментов правки и
  нет `model:`; непоправленная копия файла (агент, правило, навык), чей хеш
  записан в манифесте, при обновлении заменяется без вопроса и без копии в
  `.upgrades/`. Последнего случая не было: соседний тест
  `test_an_untouched_file_is_updated_silently` на деле проверяет первую
  установку, файла там ещё нет. Установщик не менялся.

## Как проверено (замеры, Claude Code 2.1.274)

1. **Какое имя навыка писать в `skills:`.** Пробные агенты с единственным
   инструментом WebSearch (прочитать файл нечем; TodoWrite эта версия не
   принимает — «unrecognized»), метка-«канарейка» только в теле SKILL.md.
   Установка в проект: простое имя `bead-review` — метка есть; имя
   `claude-protocol:bead-review` — метки нет, в журнале отладки
   `Skill 'claude-protocol:bead-review' specified in frontmatter was not found`.
   Плагин (`claude --plugin-dir`): оба имени работают, а если указать оба,
   текст навыка загружается дважды. Вывод: простое имя — единственное, что
   работает в обоих случаях. Субагенты при этом не вызвали ни одного
   инструмента (проверено по их журналам).
2. **Настоящий агент, установка через `npx`.** `bootstrap.py` во временный
   проект (заглушены только `bd init` и `bd doctor`), в ветке `bd-demo-1`
   заложены три ошибки (`clamp` возвращает нижнюю границу вместо верхней, нет
   `RangeError`, тесты не покрывают два критерия). `code-reviewer` нашёл все
   три, отчёт привязан к полному SHA, команды только читающие плюс `npm test`
   и воспроизведение через `node -e`, дерево не изменилось, хук SubagentStop
   ответил `approve`. В журнале: `Preloaded skill 'bead-review'`.
3. **Настоящий агент из плагина** (`--project-only` + `--plugin-dir` на эту
   рабочую копию), на haiku: `claude-protocol:code-reviewer`, навык загружен,
   те же три ошибки, хук — `approve`. Но haiku попробовал `git checkout
   bd-demo-1` в основной копии (git отказал: ветка занята рабочей копией) и
   записал в доказательство значение, которого не видел. В навык добавлено:
   никаких `checkout`/`switch`, доказательство — только то, что напечатала
   команда.
4. **Повторная проверка** на haiku: номера R1–R4 сохранились, статусы
   проставлены, но оспоренное R2 заведено заново как R5. В навык добавлено:
   незакрытая проблема сохраняет свой номер.
5. **Проверка самой ветки по навыку** (отдельный субагент на opus). Нашёл:
   хук SubagentStop в тогдашнем виде (до fyq) останавливал проверяющего,
   процитировавшего строку отчёта исполнителя как доказательство
   (воспроизведено запуском хука); совет `bd worktree create` не доводит до
   нужного коммита без `checkout`; в форме запроса был статус «answered»,
   которого не знала повторная проверка; README давал пути
   `.claude/skills/...`, которых нет при установке плагином; PR из форка не
   достаётся через `git fetch origin <ветка>`. Всё исправлено в тексте;
   второй круг — блокирующих замечаний нет.
6. **Независимая проверка ведущим** (на `6e11892`). Главное (P2): диапазон,
   заданный именами веток (`main..bd-proj-42`), сравнивался через две точки,
   и всё, что `main` получил после начала работы, выглядело удалённым
   исполнителем — на этой же ветке `main..` дал 25 файлов и 2547 удалённых
   строк против 13 файлов и 103 строк у `main...`. Теперь диапазон от имени
   ветки идёт от общего предка, диапазон из двух хешей — как задан, примеры
   переписаны на три точки и хеши. Ещё: описание хука завершения устарело
   (после fyq хук смотрит только на строку, начинающуюся с маркера) —
   в навыке теперь одно правило, не зависящее от устройства хука: `BEAD` и
   `COMPLETE` никогда не стоят в одной строке отчёта (так же сказано у
   merge-supervisor); база PR берётся из `baseRefOid` после `fetch`, а не из
   возможно устаревшей `origin/<ветка>`; для PR проверки можно запускать во
   временной выгрузке `git archive <head> | tar -x` вне репозитория, которая
   потом удаляется; `implementation-standard` велит закоммитить работу до
   передачи на проверку; перенесены строки длиннее 80 знаков.

Модель: без `model:` субагент берёт `CLAUDE_CODE_SUBAGENT_MODEL`, а если её
нет — модель сессии. На этой машине переменная задана в `env` настроек
пользователя (`opus`) и перекрывает переменную окружения процесса; перебить
её для пробного запуска можно через `--settings '{"env":{...}}'`.

## Что проверять первым, если сломается

- Агент работает «без порядка», отчёт не по форме — запустить с
  `--debug-file` и искать `Preloaded skill 'bead-review'` или
  `specified in frontmatter was not found`. Имя в `skills:` должно совпадать
  с `name:` в SKILL.md и с каталогом (это стерегут тесты
  `TestAgentsPreloadShippedSkills`).
- Хук SubagentStop останавливает проверяющего — искать в его отчёте строку,
  где стоят и `BEAD`, и `COMPLETE`: хук принимает такую строку за отчёт
  исполнителя. Форма отчёта таких строк не содержит; навык велит пересказать
  или сослаться на `путь:строка`, а не цитировать.
- В отчёте «удалены» файлы, которых задача не касалась — диапазон сравнили
  через две точки между именами веток. Навык требует общего предка
  (`git merge-base`); смотреть, какой `Base:` записан в отчёте.
- Проверяющий поменял что-то в дереве — смотреть его команды в журнале
  субагента; границы записаны и в навыке, и в теле агента.

## Доработка после первой настоящей проверки (nbr)

Навык впервые применили к задаче 69n. Проверяющий назвал три места, где
навык молчал; все три закрыты в `SKILL.md` и `handoff.md`.

- **Старая ошибка в коде, который изменение лишь использует** (в 69n —
  ошибка безопасности в `hook-utils`, заведена отдельно как mxi). Уровень P1
  «дыра в безопасности» спорил со словами «внесено не этой задачей». Теперь
  это отдельный вид замечания `Found along the way`: номер R из общей
  последовательности, доказательство по `base`, приоритет —
  подсказка для отдельной задачи, на итог не влияет, задачу заводит ведущий
  или пользователь, не проверяющий. Если изменение делает старую ошибку хуже
  или достижимой по-новому, эта часть — дефект самого изменения. При
  повторной проверке такое замечание получает статус `moved to <bead-id>` и
  дальше не повторяется.
- **Конфликт с ушедшей вперёд веткой и особые просьбы.** В шапке отчёта —
  строка `Merge outlook`; шаг 3 объясняет, как её заполнить, не трогая
  дерево: `git merge-tree --write-tree --name-only --no-messages <tip> <head>`.
  Проверено на Git 2.55: без конфликта код 0 и идентификатор дерева; при
  конфликте код 1, идентификатор и список файлов; но код 1 бывает и при
  ошибке (неизвестная ревизия), тогда идентификатора нет — поэтому навык
  смотрит на оба признака, а всё прочее пишет как `not checked`. Совет
  `gh pr view --json mergeable` убран после проверки: поле отвечает про
  текущую вершину PR, а не про зафиксированную, и часто бывает `UNKNOWN`.
  Конфликт — не замечание и итог не меняет, но после его разрешения нужна
  повторная проверка. Пункты, которые
  просили проверить особо, — необязательное поле `Points to cover` в форме
  запроса и раздел `Requested points` в отчёте со ссылкой на критерий,
  замечание или проверку.
- **Кеши от тестов.** «Оставить дерево как было» теперь значит: `git status
  --short` одинаков до и после; игнорируемые кеши (`__pycache__`,
  `.pytest_cache`, `node_modules/.vite`) не в счёт. Без них обходится
  `python -B -m pytest -p no:cacheprovider` (проверено: не остаётся ни
  одного каталога). Чистить игнорируемое (`git clean -X`) нельзя — уйдут
  `.env` и зависимости автора. Навык также прямо запрещает проверяющему
  заводить задачи.

Номера R и их сохранение между проверками, границы полномочий и запрет
ставить `BEAD` и `COMPLETE` в одну строку не менялись. Старый отчёт без новых
строк остаётся годной основой для повторной проверки: пустые разделы и так
опускаются. `templates/agents/code-reviewer.md` не тронут — он только
подгружает навык.

Независимая проверка (`code-reviewer` на `ce6d9fe`) блокирующих замечаний не
нашла. По её замечаниям: в форме отчёта перечислены все четыре исхода
`Merge outlook`; статус `moved to` оставлен только для старых ошибок (для
отложенных обычных замечаний он менял бы итог, а этого никто не просил);
правило итога считает только раздел Defects; пример повторной проверки
совпадает с номерами формы. Пока шла проверка, в `main` слили 69n, и
`README-ru.md` дал конфликт: здесь был заново перенесён весь абзац, а 69n
дописала запись сразу за ним. Перенос убран — меняется одна строка в
середине абзаца, и конфликта больше нет.

Что проверять первым: нет строки `Merge outlook` или в ней `not checked` при
известной ветке — смотреть шаг 3 (Git старше 2.38 не знает `--write-tree`);
старая ошибка попала в Defects и перевела итог в `changes needed` — смотреть,
показано ли по `base`, что она была до задачи.

Установленная копия навыка в `.claude/skills/bead-review/` основной рабочей
копии репозитория игнорируется git и после слияния останется прежней, пока её
не скопируют заново.
