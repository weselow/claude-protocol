# 2026-09-17 — доводы для `.cmd`-обёрток и процессы за ними

Исправление безопасности (задача mxi). В Windows bd и gh, поставленные через
npm, — это `.cmd`-обёртки, а их можно запустить только через `cmd.exe`.
Кавычки, которыми `hook-utils.cjs` обрамлял доводы на этом пути, держали не
каждый довод: часть довода `cmd.exe` мог прочитать не как довод. Проверка
задачи 69n это воспроизвела. Затронуты версии 3.9.2 и более ранние в Windows,
где `bd` или `gh` — `.cmd`-обёртка. Прямой запуск (`bd.exe`, `gh.exe`, git),
Linux и macOS не затронуты. Там же нашлась вторая беда: по истечении срока
останавливался только `cmd.exe`, а программа за ним работала дальше. Проверка
этой ветки добавила третью: программа, названная без пути, могла найтись в
каталоге проекта раньше, чем на `PATH`.

## Что сделано

**Отказ вместо кавычек** (`viaCmdExe`, `NOT_FOR_CMD_EXE` в
`templates/hooks/hook-utils.cjs`). Довод, в котором есть `"`, `%`, `!`, CR,
LF или NUL, через `cmd.exe` не отправляется вовсе: синхронный вызов
возвращает `null`, асинхронный — обещание с `null`, а в
`beads_orchestrator_errors.log` пишется строка `[hook-utils] not run through
cmd.exe: …` с именем программы и самим доводом (в виде JSON, не длиннее 200
знаков). Это символы, про которые известно, что они обходят кавычки; за
полноту списка никто не ручается, поэтому `cmd.exe` вдобавок запускается с
`/v:off` — отложенное раскрытие переменных можно включить в реестре для всех
`cmd.exe`, и `/d` его не выключает, а ключ командной строки главнее настройки
в реестре (так сказано в `cmd /?`; проверено, что поздний `/v:off`
перекрывает `/v:on`). Хукам эти символы не
нужны: bd и gh получают идентификаторы, имена полей и флаги, а `%` в строках
формата нужен только git (о git-обёртке — в ограничениях). Проверка идёт до
любого запуска — и при первом вызове (повтор через `cmd.exe` после отказа
прямого запуска), и когда обёртка уже известна. Комментарий над
`quoteForCmdExe` был неверен и исправлен. Удвоение косых перед кавычкой
внутри довода стало ненужным и убрано; удвоение косых в конце осталось.

**Поиск программ в каталоге проекта** (`withoutCwdSearch`, `system32`).
Программу, названную без пути, Windows ищет сначала в текущем каталоге — а
это корень проекта, — если не задана переменная
`NoDefaultCurrentDirectoryInExePath`. Claude Code её задаёт, другие способы
запуска хуков — не обязательно. Теперь на Windows `commandOptions` задаёт её
всегда, и в двух местах: в окружении самого процесса хука, потому что Node
смотрит именно его, когда ищет программу по имени (замерено: переменная в
окружении, переданном ребёнку, на поиск не влияет), и в окружении ребёнка,
потому что `cmd.exe` ищет по своему. Остальное окружение — процесса или
переданное вызывающим — сохраняется. `cmd.exe` и `taskkill.exe` запускаются
по полному пути из `%SystemRoot%\System32` (если переменной нет —
`C:\Windows`).

**Идентификаторы в `session-start`** (`confirmedBeads`, `BEAD_ID`). Перед
`bd show` догадки об идентификаторах задач проверяются: спрашиваются только
те, что состоят из букв, цифр, `.`, `_` и `-`. Набор — как в `bash-guard`, но
буквы любого алфавита: bd берёт префикс из имени каталога, а оно бывает и
русским (тест «asks about an id in any alphabet»). Все догадки уходят одним
вызовом, и неподходящая больше не оставляет без ответа остальные.

**Остановка всего дерева** (`stopChild`, `stopTree`). В Windows остановка
процесса не останавливает его потомков. Теперь по истечении срока сначала
закрываются каналы вывода (как и раньше), затем `taskkill /T /F /PID` —
пока `cmd.exe` ещё жив, потому что `taskkill` находит потомков через
родителя, — и только потом `child.kill()`. `taskkill` ждём синхронно: Node при
выходе останавливает своих прямых потомков (проверено), и хук, вышедший
сразу после срока, убил бы и сам `taskkill`. Код выхода 128 («процесс не
найден») не ошибка: так бывает, когда программа закончилась ровно к сроку,
а её выход ещё не прочитан. Остальные отказы пишутся в журнал. Процесс, выход
которого уже прочитан, не трогаем: его номер мог достаться другому.

**Синхронный путь через поток-помощник** (`settleSync`,
`SETTLE_IN_WORKER`). У `execFileSync` свой срок, и по нему он останавливает
только `cmd.exe`, а до номера процесса не дотянуться, пока вызов не вернётся.
Поэтому синхронный вызов обёртки теперь выполняет тот же `settle`, что и
асинхронный, в отдельном потоке (`worker_threads`), а основной поток ждёт на
`Atomics.wait` и забирает ответ через `receiveMessageOnPort`. Поток
загружает `hook-utils.cjs` сам, поэтому `settle` теперь в экспорте. Ожидание
длится срок команды плюс 5 секунд (запуск потока и `taskkill`); поток отвечает
при любом исходе и отличает неудачу команды (`failed`) от собственной
(`broken`: файл не загрузился, `settle` нет или он упал). Собственная неудача
потока, отсутствие ответа и невозможность передать потоку параметры пишутся
в журнал. Прямой запуск программ (git, `bd.exe`) остался на `execFileSync` и
ничего не стал стоить.

Цена замерена на `.cmd`-обёртке вокруг настоящего `bd.exe`: вызов через
`cmd.exe` занимал ~210 мс, теперь ~235 мс, то есть около 25 мс на вызов. В
начале сессии таких синхронных вызовов один-два.

**Проверка на настоящем хуке.** `session-start` с `bd.cmd`, который зависает:
старая версия вышла через 40 с и оставила 5 работающих процессов bd (один от
`bd version`, четыре от списков задач), новая — через 41 с и ни одного.

## Что проверять первым, если сломается

- **Хук перестал видеть bd или gh, а раньше видел.** Посмотреть
  `beads_orchestrator_errors.log` в корне проекта: строка `not run through
  cmd.exe` значит, что какой-то вызов получил довод с одним из запрещённых
  символов. Искать вызывающее место, а не ослаблять проверку.
- **Все вызовы обёрток дают `null`.** Проверить, что поток запускается:
  `node -e "console.log(require('./templates/hooks/hook-utils.cjs').execCommand('bd',['version']))"`
  при `bd.cmd` на `PATH`. Сбой потока пишется в журнал строкой `waiting for
  cmd.exe on a worker thread failed: …`; `the worker never answered` в ней
  значит, что поток не ответил за срок плюс 5 секунд, `the worker could not
  run it` — что он не смог даже начать.
- **Программа не находится, хотя лежит в проекте.** Так и задумано: программа
  по имени ищется только на `PATH`.
- **После зависшего bd снова остаются процессы.** Проверить, что `stopTree`
  вызывается до `child.kill()` и что `%SystemRoot%\System32\taskkill.exe`
  существует. Строка `taskkill could not stop the process tree` в журнале
  покажет код отказа.
- **Тесты.** `tests/hooks/hook-utils.test.js`: отказы, остановка дерева,
  сбои потока и «programs of the same name in the project directory» —
  только в Windows, в других системах пропускаются с пояснением;
  `tests/hooks/session-start.test.js`: «asks bd only about names a bead id
  can have».

## Известные ограничения

- git, который сам — `.cmd`/`.bat`-обёртка (так бывает, когда первым на
  `PATH` стоит depot_tools), остаётся без ответа на вызовы со строкой формата
  (`--format=%H %gs`, `--format=%(refname:short)` в `session-start`): в них
  есть `%`. Проверка слитых рабочих копий тогда молчит.
- Если `cmd.exe` закончился сам, а оставленный им процесс держит канал вывода,
  по сроку этот процесс не остановится: родителя уже нет, и `taskkill /T` его
  не найдёт.
- Прямой запуск (не обёртка) в синхронном пути по-прежнему останавливает по
  сроку только сам процесс — например, git без своих помощников.
- С `timeout: 0` (без срока) синхронный вызов обёртки ждёт поток бессрочно,
  как и раньше ждал `execFileSync`. Таких вызовов в хуках нет.
- Хук на Windows меняет окружение собственного процесса (задаёт
  `NoDefaultCurrentDirectoryInExePath`) — иначе Node эту переменную не видит.
- Тесты, которые идут только в Windows, в CI не запускаются: там только
  Linux. Это отдельная задача.

## Что осознанно не тронуто

- `bash-guard.cjs`: его идентификатор уже ограничен набором
  `[A-Za-z0-9._-]`.
- Экранирование этих символов вместо отказа: отказ проще, а вызывающим они
  не нужны.
